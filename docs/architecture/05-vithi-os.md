## 1. หลักการ: 1 ขณะจิต = 1 scheduling quantum

ใน OS ทั่วไป หน่วยเวลาที่ scheduler มอบให้โปรเซสคือ **quantum** — สั้นมาก, ไม่มี state ค้างระหว่าง quantum, และทุก quantum ต้องจบด้วยการคืนสิทธิ์ให้ตัวจัดคิว

ในอภิธรรม หน่วยเวลาที่เล็กที่สุดของชีวิตคือ **1 ขณะจิต** ซึ่งมีลักษณะตรงกัน 3 ข้อ:

| ลักษณะของขณะจิต | กลไก OS ที่เทียบได้ |
|---|---|
| เกิด-ดับทันที (uppāda-nirodha) | quantum จบในตัว ไม่มี state ค้าง |
| สืบต่อเป็นสาย (santati) | scheduler วนลูปต่อไปไม่หยุด |
| มีอารมณ์เดียวต่อ 1 ขณะ | 1 quantum ประมวลผล 1 งาน |

> ⚠️ ยังไม่ตรวจสอบ: การเทียบ "ขณะจิต = quantum" เป็น *การเทียบเชิงโครงสร้าง* (structural analogy) ไม่ใช่ข้อพิสูจน์ว่าจิตคือ scheduler — เช่นเดียวกับที่ [01-mapping.md](./01-mapping.md) เตือนเรื่อง `fn` = จิต

**ข้อควรระวังที่สำคัญที่สุด:** โปรเจกต์นี้ **ไม่ได้** จัดคิว thread ของ OS จริงด้วยวิถีจิต — เป็นแบบจำลองแนวคิดที่ใช้ *ตีความ* log/event เท่านั้น (ดู § 7)

## 2. วิถี 17 ขณะ (ปัญจทวาร) = Interrupt Path เต็มรูปแบบ

นี่คือเส้นทางที่ "ภัยมาจากภายนอก" — มี hardware ยิงสัญญาณเข้ามา จึงต้องผ่านด่านรับสัญญาณจริง

| # | ขณะ | OS stage | ทำอะไร |
|---|---|---|---|
| 1 | อดีตภวังค์ | idle loop รอบก่อน | history ที่อ่านได้อย่างเดียว |
| 2 | ภวังคจลนะ | interrupt line ถูกยก (wake-up) | idle loop รู้ว่ามีสัญญาณรอ |
| 3 | ภวังคุปัจเฉทะ | **context switch เริ่ม** | ตัด idle loop เพื่อรับงาน |
| 4 | ปัญจทวาราวัชชนะ | **interrupt vector dispatch** | เลือกทางเข้าให้ตรงทวาร (ตา/หู/จมูก/ลิ้น/กาย) |
| 5 | ปัญจวิญญาณ (จักขุวิญญาณ ฯลฯ) | **ISR / driver DMA** | ดึงข้อมูลเข้าบัฟเฟอร์ |
| 6 | สัมปฏิจฉนะ | เข้า kernel ring buffer | รับ event เข้าคิว |
| 7 | สันตีรณะ | **classify / inspect** | ตีความว่าเป็นอารมณ์อะไร น่ากังวลแค่ไหน |
| 8 | โวฏฐัพพนะ | **Policy Decision Point (PDP)** | ตัดสินว่าจะ execute หรือไม่ |
| 9 | ชวนะ ×7 | **execution window** | ลงมือทำ และเขียนผลลง log |
| 10 | ตทาลัมพนะ ×2 | flush ผล + คืนบัฟเฟอร์ | บันทึกผลแล้วกลับสู่พัก |
| — | กลับภวังค์ | กลับเข้า idle loop | จบ quantum |

**จุดที่ต้องจำ:** `ปัญจวิญญาณ` คือ **ISR** — เป็นโค้ดที่รันในบริบทของ interrupt ไม่ใช่ user space และ `โวฏฐัพพนะ` คือ **ประตู syscall** ที่ตัดสินใจก่อนจะยอมให้ทำงานจริง

## 3. วิถี 15 ขณะ (มโนทวาร) = Internal Event Path

นี่คือเส้นทางที่ "ภัยมาจากภายใน" — ไม่มี hardware ยิงสัญญาณ ไม่มีผู้บุกรุก มีแต่ event ที่เกิดในระบบเอง (log, queue, timer)

| # | ขณะ | OS stage | ทำอะไร |
|---|---|---|---|
| 1 | อดีตภวังค์ | idle loop รอบก่อน | history |
| 2 | ภวังคจลนะ | wake-up signal (soft) | รู้ว่ามี event รอ |
| 3 | ภวังคุปัจเฉทะ | context switch | ออกจาก idle |
| 4 | มโนทวาราวัชชนะ | **internal event dispatch** | หยิบ event จากคิวภายใน (ไม่มี IRQ) |
| 5 | มโนวิญญาณ | อ่าน event | ไม่มี driver — อ่านจากหน่วยความจำโดยตรง |
| 6 | โวฏฐัพพนะ | **PDP** | ตัดสิน |
| 7 | ชวนะ ×7 | **execution window** | ลงมือทำ |
| 8 | ตทาลัมพนะ ×2 | flush | บันทึกผล |
| — | `Bhavanga` | กลับ idle | *(ประกาศไว้ใน enum แต่ลำดับ 15 ขณะยังไม่ append ขณะนี้)* |

**สิ่งที่หายไปเทียบกับวิถี 17:** `ปัญจทวาราวัชชนะ` (interrupt vector) และ `ปัญจวิญญาณ` (ISR) — เพราะไม่มี hardware เกี่ยวข้อง นี่คือเหตุผลเชิง OS ว่าทำไมวิถีมโนทวารจึงสั้นกว่า: **ไม่มีด่านฮาร์ดแวร์ให้ผ่าน**

---

## 4. ทำไม 15 กับ 17 ต่างกัน — และข้อที่ต้องระวัง

### 4.1 คำอธิบายเชิง OS
- **17 ขณะ = full interrupt path** — มี ISR, มีการตีความอารมณ์ (สันตีรณะ) ครบ
- **15 ขณะ = internal path** — ตัด ISR ออก เพราะ event มาจากภายใน

### 4.2 ข้อเท็จจริงเรื่องจำนวนขณะ (ต้องรายงานตรงไปตรงมา)
คัมภีร์อภิธรรมนับ **มโนทวารวิถีปกติเป็น 13 ขณะ** (ภวังค์ 3 + มโนทวาราวัชชนะ 1 + ชวนะ 7 + ตทาลัมพนะ 2)

แต่ **โปรเจกต์นี้ใช้ 15 ขณะ** — คือ 13 ขณะนั้น **บวก `มโนวิญญาณ` และ `โวฏฐัพพนะ` เพิ่มเข้ามา 2 ขณะ** ตามที่ [`vithi.rs`](../../core/src/paramattha/vithi.rs) ประกาศไว้เองใน doc comment

> ⚠️ ยังไม่ตรวจสอบ: การเพิ่ม 2 ขณะนี้เป็น **การออกแบบของโปรเจกต์** ไม่ใช่การนับตามตำรา และยังไม่ได้ตรวจทานกับคัมภีร์ในรอบนี้ — ถ้าจะอ้างอิงภายนอกต้องตรวจก่อน

ในเลนส์ OS การเพิ่ม 2 ขณะนี้มีเหตุผลเชิงวิศวกรรมที่อธิบายได้: มันคือการ **เพิ่ม stage `inspect` และ stage `PDP` เข้าไปใน fast path** ให้ทุกลูปมีการตัดสินใจชัดเจน ไม่ปล่อยให้ decision ถูกกลืนไปกับ stage รับ event

## 5. ชวนะ 7 = Execution Window (จุดที่ระบบ "ลงมือทำ")

นี่คือส่วนที่สำคัญที่สุดในเชิง OS และเป็นจุดที่โค้ดจริงบอกอะไรที่เอกสารทั่วไปไม่บอก

ใน [`vithi.rs`](../../core/src/paramattha/vithi.rs) ชวนะทั้ง 7 ขณะถูกสร้างด้วย `CetasikaVector` **ชุดเดียวกัน** ทั้ง 7 ครั้ง:

```rust
moments.extend((0..JAVANA_COUNT).map(|_| CittaJati::Javana(c)));
```

**ความหมายเชิง OS:** การตัดสินใจถูกทำ **ครั้งเดียว** ที่ `โวฏฐัพพนะ` (PDP) — ชวนะ 7 ขณะไม่ใช่การ "โหวตซ้ำ" หรือ "ทบทวนใหม่" แต่คือ **การยืนยันผลการตัดสินใจเดิม 7 จังหวะ**

เทียบกับ OS ได้กับการที่ kernel ตัดสินใจแล้วว่า "จะ execute" จากนั้นจึงเขียนผลลง append-only log ติดกัน 7 ระเบียน — ถ้าตัดสินใจผิด ก็ผิดซ้ำทั้ง 7 ระเบียน นี่คือเหตุผลเชิงสถาปัตยกรรมว่าทำไมคุณภาพของ `โวฏฐัพพนะ` (PDP) จึงสำคัญกว่าจำนวนรอบของชวนะ

> **ข้อสรุปเชิงออกแบบ:** ถ้าจะเพิ่มความปลอดภัย อย่าเพิ่มจำนวนชวนะ — ให้เพิ่มคุณภาพการตรวจที่ `โวฏฐัพพนะ` และ `สันตีรณะ` เพราะชวนะไม่ได้ตัดสินใจซ้ำ

## 6. PDP = `โวฏฐัพพนะ` (จุดเชื่อมกับมรรค 8)

| แนวคิด | ในอภิธรรม | ใน OS | ในโค้ด |
|---|---|---|---|
| จุดตัดสินใจ | โวฏฐัพพนะ | PDP / syscall gate | [`CittaJati::Votthapana`](../../core/src/paramattha/vithi.rs) |
| การตีความก่อนตัดสิน | สันตีรณะ | classifier | *ยังไม่มีโค้ด* |
| การรับ event | มโนทวาราวัชชนะ | event dispatch | [`CittaJati::Manodvaravajjana`](../../core/src/paramattha/vithi.rs) |
| เจตนา (กุศล/อกุศล) | ชวนะ + เจตสิก | action ที่ commit | `Vithi15::is_akusala()` |

**การเชื่อมกับมรรคข้อ 1 (สัมมาทิฏฐิ):** ใน [`02-security.md`](./02-security.md) สัมมาทิฏฐิถูกวางเป็น *root of trust* ระดับ boot — ในเลนส์วิถีจิต มันคือ **เกณฑ์ที่ใช้ตัดสินที่ `โวฏฐัพพนะ`** ว่าอะไรถือว่า "จริง" ก่อนอนุญาตให้ชวนะลงมือ

การตรวจ "มิจฉาทิฐิ" จึงไม่ใช่การตรวจที่ชวนะ แต่คือการตรวจ **เจตสิกที่ประกอบกับชวนะ** ย้อนไปยัง `moha` / `ditthi` ใน [`spec/Paramattha-Cetasika.json`](../../spec/Paramattha-Cetasika.json)

## 7. ชวนะ 7 → รูป 4 ธาตุ (Kamma Impact)

ขั้นนี้ตอบคำถามว่า **"ชวนะอกุศลไปทำอะไรต่อ"** ในโค้ด [`kamma_impact.rs`](../../core/src/paramattha/kamma_impact.rs)

หลักการเดียวกับ § 5: มีเพียง **ชวนะ** ที่สั่งสมกรรม ขั้นอื่นเป็นวิบาก/กิริยา ไฟล์นี้จึงอ่าน
`CetasikaVector` **เฉพาะชวนะ** แล้วแปลงเป็นผลต่อธาตุทั้ง 4 ที่จำลองไว้ใน [`mahabhuta.rs`](../../core/src/paramattha/mahabhuta.rs)

`CetasikaVector` เก็บเจตสิกครบ **52 มิติ** เป็น `[f32; 52]` เรียงตาม index ใน [`cetasika.rs`](../../core/src/paramattha/cetasika.rs)
ซึ่งตรงกับ `spec/Vattapada-7.json` → `cetasika_registry.canonical_52` (เทสต์บังคับไว้)
เข้าถึงด้วยค่าคงที่ index เช่น `cetasika.get(MOHA)` หรือ `cetasika.get(ADOSA)`

| ธาตุ (รูป) | ตัวแปรที่เปลี่ยน | เจตสิกที่ทำให้เสื่อม | เหตุผลเชิงอุปมา |
|---|---|---|---|
| ปฐวี (ความคงรูป) | `pathavi.wear_level` ↑ | โลภะ + โทสะ + โมหะ | อกุศลทุกชนิดสึกกร่อนความคงรูป |
| อาโป (ความเกาะกุม) | `apo.cohesion_strength` ↓ | โลภะ | ยึดติดเกินเหตุจนโครงสร้างไม่เกาะกุม |
| เตโช (ความร้อน) | `tejo.temp_c` ↑ | โทสะ | โทสะคือความร้อน เผาตัวเอง |
| วาโย (การเคลื่อน) | `cluster.vayo_turbulence` ↑ | โมหะ | โมหะคือความฟุ้ง/สับสนของสัญญาณ |

**หมายเหตุเรื่องชื่อเจตสิก:** ทะเบียน 52 ไม่มี id `metta` — เมตตาในที่นี้คือ `adosa` (อโทสะ)
ซึ่งเป็นเจตสิกที่ตรงข้ามกับโทสะจริง ส่วน "เมตตา" ในความหมายอัปปมัญญาเป็นอีกกลุ่มหนึ่ง

กุศลชวนะ (สติ/เมตตา) ให้ผลตรงข้าม: ทำให้เย็นลง (`tejo_cooling`), คืนความเกาะกุม (`apo_recovery`),
บรรเทาความสึกกร่อน (`pathavi_relief`) และคลายความฟุ้ง (`vayo_calm`)

```rust
let mut cluster = RupaCluster::new();
cluster.absorb_vithi17(&vithi);          // รับผลของหนึ่งวิถี
cluster.degradation();                    // 0.0 = สมบูรณ์, 1.0 = เสื่อมสุด
```

**จุดที่ต้องจำ 3 ข้อ:**

1. **วิถีที่ถูกบล็อกไม่มีผลเลย** — ถ้า `Vithi17` หยุดที่โวฏฐัพพนะ จะไม่มีชวนะ → `RupaImpact::none()`
   (มีเทสต์ `blocked_vithi_has_no_impact`)
2. **หนึ่งวิถี = หนึ่งเหตุการณ์** — ผลรวมของชวนะ 7 ขณะถูกหารด้วย `JAVANA_COUNT`
   เพื่อไม่ให้ความรุนแรงคูณเจ็ด (มีเทสต์ `one_vithi_does_not_multiply_harm_by_seven`)
3. **`VayoDriver` เป็น unit struct** — ไม่มีสถานะ จึงเก็บความฟุ้งไว้ที่ `RupaCluster.vayo_turbulence`
   แทนการแก้ struct เดิม

> ⚠️ **ข้อจำกัด:** ตารางนี้เป็น **อุปมา (analogy)** ตามกติกา [`docs/GLOSSARY.md`](../GLOSSARY.md) ข้อ 5
> ไม่ใช่หลักในตำรา และน้ำหนักตัวเลข (`HEAT_PER_DOSA = 40.0` ฯลฯ) ตั้งขึ้นเพื่อให้ทดสอบได้ ไม่ได้มาจากคัมภีร์

> **ย้ำ:** "Scheduler" ในเอกสารนี้เป็น **ชื่อเชิงแนวคิด** ไม่ใช่ scheduler ที่รันอยู่ — ระบบปัจจุบันใช้ `Vithi15` เพื่อ *ตีความ* log ภายในว่าเป็นภัยประเภทใด ไม่ได้ใช้จัดลำดับการทำงานของโปรเซส
